# JINGS 営業標準デモ

製造業向けの商談でそのまま使える動くデモ集。**7本すべてが同一の架空企業データを共有**しているため、複数を続けて見せても話が破綻しない。

実顧客のデータは一切含まない。どの見込み客にもそのまま見せられる。顧客固有データを使うデモは各案件フォルダ側で個別に作る。

## 架空企業

**JINGSデモ精機株式会社** — 自動車用電動アクチュエータ・車載センサユニットの設計製造。

| 製品 | 状態 | デモでの役割 |
|---|---|---|
| ACT-210 | 量産中 | 過去不具合の蓄積元 |
| ACT-220 | 量産中（主力） | 工程FMEA・不具合検索の主役 |
| ACT-230 | 設計中 | 設計変更・DRBFM・DRの対象 |
| SNS-100 | 量産中 | 別ラインの比較対象 |

工程10〜19（樹脂成形→圧入→ギヤ組付→モータ組付→はんだ→配線→グリス→締結→機能検査→気密検査）。
不具合記録・工程FMEA・設計変更通知・図面・設計審査記録が**相互に紐づいている**（不具合 → FMEA行 → 設計変更 → 図面）ので、デモ間で「同じ話の続き」ができる。

## 使う（営業メンバー）

社内URLをブックマークして開く。ホスティング設定後にURLを記載する。

URLがまだ無い間は `dist/` を丸ごとダウンロードし、`index.html` をChromeで開く。

## 作る・直す

```bash
python3 build.py              # 全デモ + トップページを dist/ へ
python3 build.py 01-knowledge # 1本だけ
python3 verify.py             # Playwrightで全デモの導線を検証
```

ビルド後は必ず両方を通す。

```bash
python3 ~/.claude/skills/jings-demo-system/scripts/check_demo.py dist/01-knowledge.html
```

### 構成

| パス | 役割 |
|---|---|
| `src/common/data.js` | **共通データセット。全デモがこれを参照する** |
| `src/common/style.css` | 共通CSS（jings-demo-system の design-system.md 準拠） |
| `src/common/shell.js` | 共通JS（画面切替・根拠パネル・通知・段階ローダー・CSV出力） |
| `src/demos/<id>/meta.json` | タイトル・ナビ・トップページ用の紹介文 |
| `src/demos/<id>/body.html` | 画面（view）のHTML |
| `src/demos/<id>/app.js` | そのデモのロジック |
| `dist/` | 出力。単一HTML・外部依存なし・オフライン動作 |

ヘッダー・サイドナビ・根拠パネル・通知領域は `build.py` が `meta.json` から生成する。**7本のUIを揃えるため、各デモ側でヘッダーやナビを書かない。**

### デモを1本追加する手順

1. `src/demos/<番号>-<名前>/` を作り、`meta.json` / `body.html` / `app.js` を置く
2. 画面は `<section class="view" data-view="...">` で作る（最初の1つ以外は `hidden`）
3. データは `src/common/data.js` から取る。**新しいデータが必要なら data.js に足す**（デモ側に閉じたデータを持たせない）
4. `verify.py` の `CHECKS` に検証関数を追加する
5. `build.py` → `check_demo.py` → `verify.py` の順に通す

## デモ2の推奨説明順（商談用）

工程は **10（樹脂ハウジング成形）** を使う。新規候補・抜け漏れ候補・AI推定の要求事項の3つが揃うため、説明したいことが全部見せられる。

1. 左の入力パネルで工程10を選び「抜け漏れ展開」のまま生成する
2. **①機能** — 「工程フローから機能を整理した」ことを見せる。起点が工程であることが品証・生技に効く
3. **②要求事項** — 出典の文書名と該当箇所が出る。1件が「AI推定・要確認」になっているのを必ず指摘する（推定値を規格値として出さない設計）
4. **③故障モード** — 「要求事項 → 逸脱の型 → 故障モード」の列を左から順に読む。原因や影響と混同していないことを示す
5. 「根拠資料を確認する」を押す。**導出の連鎖がパネルで全部追える**のがこのデモの核心
6. S・O・Dは「AI候補・要確認」。引き当て元がない行は「未評価」で点数を作らないことを示す
7. **抜け漏れ候補** — 「他工程では登録済みの逸脱の型が、本工程にない」という出し方を説明する
8. 「ドラフトへ採用」を1件押す。**自動では入らない**＝FMEAの責任の所在が人に残ることを示す
9. Excel出力（20列・AI提案と人の確定の区分を含む）

工程17を選ぶと抜け漏れ候補が0件になる。これは不具合ではなく、登録が充実している工程では無理に候補を出さない設計。聞かれたらそう答える。

## 各デモの見せ場（商談で必ず押すところ）

| # | 見せ場 | ひとこと |
|---|---|---|
| 1 | 「根拠を確認する」 | 出典の帳票名と原文が出る。さらにその不具合を出典とするFMEA行・設計変更まで辿れる |
| 2 | 要求事項→逸脱の型→故障モードの列 | 起点が工程であること、原因や影響と混同していないことが一目で分かる |
| 3 | **生成途中で止まる確認モーダル** | AIが類似判定を勝手に決めない。設計部門への信頼演出はここが最大 |
| 3 | 4系統バッジ | 「過去データを検索してるだけでは？」に先回り。緑（機能演繹）黄（物理推論）が過去実績のない領域 |
| 4 | 標準項目を1件も削っていないこと | AIは優先度を付けるだけ。落とす判断は主査が持つ |
| 5 | 「設計意図の妥当性は確認していません」 | 検図ルールに対する不足しか見ないと明言する。過信を防ぐ |
| 6 | **空欄のまま出るD1・D8** | 顧客提出物を推測で埋めない。埋めない理由を画面で説明する |

デモ3のモーダルは「条件付きで引き継ぐ（推奨）」を選ぶと、過去実績由来の行に「要再評価」が付く。「別部材として扱う」を選ぶと過去実績の行が消えて演繹系統だけになる。**選択で結果が変わることを見せると刺さる。**

## 帳票（出典の実物）

出典ボタンを押すと、帳票の**実物**が表示される。AIが描いた絵ではなく、`data.js` の内容から
**実際の .xlsx を生成し、LibreOffice でレンダリングしたもの**。行番号・列記号・罫線を出しているので
Excelで開いた画面と同じ見え方になる。

```bash
python3 sheets/gen_sheets.py   # data.js から xlsx を生成 → sheets/out/
python3 sheets/snap.py         # xlsx → PDF → PNG → sheets/sheets.json（data URI）
python3 build.py               # meta.json の sheets に挙げたキーだけを各デモへ埋め込む
```

| 帳票 | 使うデモ |
|---|---|
| 工程FMEA（AIAG-VDA様式・表紙/改訂履歴つき） | 1・2・3・5 |
| 苦情報告書（不良現象8分類・14件） | 1・4・6 |
| 設計変更発議書 | 3 |
| 工程フロー図・QC工程表 | 2 |
| 設計審査記録（DR3チェックシート） | 4 |
| 図面属性表・検図チェック記録 | 5 |

**商談では実ファイルを開くのが最も効く。** `dist/帳票サンプル/` に同じ xlsx を置いてあるので、
Excelで開いて見せられる。デモ内の画像はその代わり（アプリを切り替えられない場面用）。

図面そのものの画像は作っていない。実物のCAD/PDF図面がないため、絵を描いて実物のように見せることはしない。
デモ5では「AIが図面から読み取った寸法・公差・注記」を図面属性表として実物Excelで示している。

## 守っているルール

`jings-demo-system` スキルの設計原則に従う。特に次の4点は商談での効き目に直結するので崩さない。

1. **AIが評価を自動確定しない。** S・O・Dやリスクは候補まで。確定は担当者。
2. **全候補に根拠を付ける。** 出典の文書名と原文を根拠パネルで示す。
3. **AI提案と確定情報を区別する。** ステータスラベルで明示する。
4. **行き止まりを作らない。** ボタンは必ず結果かフィードバックを返す。空状態には次の手を書く。
